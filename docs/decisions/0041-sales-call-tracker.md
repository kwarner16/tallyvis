# 0041 — Sales Call Tracker V1 (internal admin cold-calling tool)

## Status

Accepted. A new internal admin feature, built in one evening to be usable
for cold calling the next morning. Deliberately NOT a general-purpose CRM
— see "Intentionally deferred" below for the long list of things this
does not do.

## Why this exists

Kyle needed to paste a prospect list (generated by ChatGPT) into
TallyVis, have it detect businesses he's already contacted, and then
work through the remaining prospects one by one with almost zero
administrative overhead — look at the screen, click Start Call, dial the
phone himself, talk, click End Call, pick an outcome, maybe type one
sentence, click Save & Next Call, dial the next number. Every
unnecessary click matters. This is internal-only; no normal TallyVis
business ever sees or is affected by any of it.

## Architecture

Follows this repo's existing admin-feature shape exactly (closest
precedent: the Founding Creator Program, ADR 0040) rather than inventing
anything new:

- **Repositories** (`repositories/salesProspects.ts`,
  `repositories/salesCalls.ts`) — the only files that write SQL, plain
  `TEXT`/`INTEGER` columns, ISO-string timestamps, `makeId()`-generated
  ids, the same conventions every other table in this schema already
  uses.
- **Services** (`services/salesProspects.ts`, `services/salesCalls.ts`,
  `services/salesImportParsing.ts`) — every exported admin function
  independently re-checks `isAdminSession` before touching data, the
  same defense-in-depth `services/admin.ts`/`services/creators.ts`
  already establish. `salesImportParsing.ts` is pure (no database
  access) so the paste-parsing logic is trivially unit-testable on its
  own.
- **Admin pages** (`apps/app/src/app/admin/sales/**`) — gated by the
  exact same `requireAdminContext()` every other `/admin/*` page uses,
  styled with the exact same Tailwind tokens/`buttonVariants`/
  `MetricCard`/`EmptyState` components already in use — no new design
  system.
- **Constants** (`packages/config/src/salesCallTracker.ts`) — outcome/
  objection enums and their display labels, shared between
  `services/api` (validation) and `apps/app` (UI), the same
  "policy/display constants live in packages/config" shape
  `creatorProgram.ts`/`plans.ts` already use.

## Schema (migration `0017_sales_call_tracker.sql`)

Purely additive — two new tables, nothing existing changes shape.

```
sales_prospects: id, business_name, contact_name?, phone,
  normalized_phone?, email?, website?, city?, state?, source?,
  created_at, updated_at

sales_calls: id, prospect_id, started_by_user_id, started_at, ended_at?,
  duration_seconds?, outcome?, notes, objections_json, follow_up_at?,
  created_at
```

No `CHECK` constraints anywhere — consistent with this schema's existing
precedent (no other migration uses one). Outcome/objection values are
validated and enumerated in the application layer
(`@tallyvis/config`'s `isSalesCallOutcome`/`isSalesObjection`), the exact
same shape `creators.status`/`isCreatorStatus` already uses.
`objections_json` follows this schema's existing `*_json` TEXT-column
convention (see `0001_core.sql`'s own comment) rather than a real
array/JSONB column, since the app only ever round-trips it through
`JSON.stringify`/`JSON.parse` and never queries into it via SQL.

**One real database constraint**: `idx_sales_calls_one_active_per_user`,
a partial unique index on `sales_calls(started_by_user_id) WHERE
ended_at IS NULL`. This is what makes "prevent accidental creation of
multiple simultaneous active calls for the same admin" actually true —
not just application discipline. A test
(`startSalesCallAdmin > the database itself refuses two simultaneous
active calls...`) proves this by bypassing the service layer entirely
and inserting directly through the repository.

## Duplicate detection strategy

**Primary signal: normalized phone number**, reusing the exact
`normalizePhoneNumber` function `services/business.ts` already uses for
SMS sending (E.164 output) — not a new phone-parsing implementation. One
gap was found and closed with a small, local wrapper
(`normalizeSalesPhoneNumber` in `services/salesProspects.ts`): the
shared function's `+`-prefixed fast path requires an already
whitespace-free string, but this feature's own spec explicitly requires
`+1 352 555 1234` (with spaces) to normalize correctly. The wrapper
strips whitespace before delegating to the shared function —
`services/business.ts` itself, and the SMS sending that depends on it,
is untouched.

A row's phone normalization failing entirely (unparseable) marks that
row **invalid** in the import preview — it is never imported, since it
could never be deduped later anyway and the spec's own minimum bar for a
"usable prospect" is a business name AND a phone number.

**Secondary signal: exact business name match** (case-insensitive) —
used ONLY to flag a **possible duplicate** for manual review, never as a
primary dedup key (names vary too much to trust alone, per the brief's
own explicit instruction). A possible-duplicate row is reported but not
auto-imported in V1 — if it really is a new business, re-pasting with a
slightly different name (or just accepting the manual review) is the
V1 answer; a "force import anyway" override was deliberately left out to
keep the import flow to exactly one decision ("new" vs. "not new"),
not two.

**Website/domain matching was considered and deliberately deferred** —
the brief explicitly allowed skipping it ("do not overcomplicate V1"),
and business-name matching already covers the softer "might be the same
business" signal reasonably well without a second heuristic to maintain.

**Within a single pasted batch**, a second row sharing an already-seen
normalized phone (whether or not that phone exists in the database yet)
is classified a duplicate of the first — so importing a list with an
internal repeat never creates two rows for the same number, and
re-importing the identical list a second time creates zero new rows
(every row now matches an existing database row by phone).

**Preview vs. commit**: `commitProspectImportAdmin` never trusts
anything the browser displayed — it re-parses and re-classifies the
SAME raw pasted text from scratch, server-side, exactly like the preview
did, before writing anything. The UI's "Import N New Prospects" button
submits the raw text itself (in a hidden field), not a list of "these
rows are new" flags, so there is no way to tamper with which rows get
imported by editing the DOM.

## Call lifecycle

1. **Start Call** (`startSalesCallAdmin`) stamps `started_at`
   server-side — this, not any browser-held value, is the timer's
   source of truth. If this admin already has an active (unfinished)
   call, it returns that SAME call instead of creating a second one —
   so clicking "Start Call" on a different prospect while one is already
   in progress can never silently open two active calls; the UI also
   disables every "Start Call" button while one is active, so this path
   is a graceful fallback, not the primary guard.
2. The in-call screen (`/admin/sales/call/[id]`) shows the prospect's
   business name, contact, phone, website, location, and prior call
   history for the SAME prospect (relevant on a follow-up call) — and a
   ticking timer computed by re-reading `Date.now() - startedAt` every
   second, never from any client-only "time I clicked Start" state. A
   page refresh mid-call reloads the same active call from the database
   and the timer picks up exactly where it should — it is never lost.
3. **End Call** is a pure client-side UI transition — it reveals the
   fast outcome form immediately (no server round trip), stops the
   visible timer, and does not yet write anything to the database.
4. **Save & Next Call** (`endSalesCallAdmin`) is the one write that ends
   the call: outcome, notes, objections, and an optional follow-up time
   are all validated and persisted together with `ended_at`/
   `duration_seconds` (computed server-side from the real elapsed time)
   in a single update. There is deliberately no intermediate "ended but
   no outcome yet" state — refreshing after clicking End Call but before
   Save just shows the still-active call again, and clicking End Call a
   second time is harmless.
5. After saving, the admin is redirected to `/admin/sales`. "Immediately
   advance to the next appropriate prospect" is satisfied by the
   **queue's own ordering** (next section) putting the right prospect at
   the top — not by auto-starting a new call without a deliberate click.
   Placing a real phone call should always be an intentional action.

**Connection status vs. sales outcome**: rather than a second field to
fill in, "was a human actually reached" is DERIVED from the outcome
(`CONNECTED_SALES_CALL_OUTCOMES` in `packages/config`) — every outcome
except `no_answer`/`voicemail` counts as connected. One fact instead of
two that could disagree, and one fewer click per call.

## Queue ordering / follow-up behavior

`listProspectQueueAdmin` ranks prospects: a due/overdue follow-up first,
then a never-contacted prospect, then one that's been worked with no
pending follow-up, last. "Due" is driven ENTIRELY by a call's own
`follow_up_at` timestamp — never implied merely by choosing the
`follow_up` outcome label. Only a prospect's MOST RECENT completed call
counts toward whether it currently has a due follow-up
(`listFollowUpsDue`'s `DISTINCT ON`), so a later call that didn't set a
new follow-up correctly clears an earlier, now-stale one rather than
leaving it stuck forever.

The dedicated "Follow-ups due" section on `/admin/sales` shows these
same entries with full context (last outcome, notes, when); the general
queue table below it excludes them, so a follow-up never gets "lost" by
also appearing, diluted, at the bottom of the cold list.

## Metrics — exact definitions

Every number is derived directly from completed (`ended_at IS NOT
NULL`) `sales_calls` rows; nothing touches `businesses`/`subscriptions`.

- **Total calls** — count of completed calls in the selected period.
- **Calls today** — count of completed calls whose `started_at` falls
  on the current UTC calendar day (this repo's existing date-math
  convention is UTC-based throughout; a single admin in one timezone
  makes the rare midnight-boundary edge case immaterial).
- **Answered / conversations** — completed calls whose outcome is in
  `CONNECTED_SALES_CALL_OUTCOMES`.
- **No answer** / **Voicemail** — exact outcome counts.
- **Interested** / **Demos** / **Follow-ups** / **Signed up** — exact
  outcome counts for `interested`/`demo_requested`/`follow_up`/
  `signed_up` respectively. ("Follow-ups" here is the OUTCOME count, a
  different number from the queue's forward-looking "follow-ups due.")
- **Call → signup rate** — signups ÷ total calls in the period; `0`
  (never `NaN`) when there are zero calls.
- **Conversation → signup rate** — signups ÷ answered calls in the
  period; `undefined` (rendered as "—") when there are zero answered
  calls, rather than a divide-by-zero.
- **Average call duration** — mean `duration_seconds` across completed
  calls that have one (every completed call does); `undefined` when
  there are none.

`getTodaySalesSummaryAdmin` powers the page-top "Today" summary
specifically: calls/answered/interested/signed-up are scoped to today's
calls, while `followUpsDueCount` is deliberately NOT scoped to today —
it's the same forward-looking "due now or overdue" count the dedicated
follow-up section shows, matching the brief's own framing of that line
as distinct from the day's call activity.

## Signed up ≠ paid customer

A `signed_up` call outcome is a plain string value on a `sales_calls`
row — nothing more. It never creates, links, or implies a `Business`
row, a `Subscription` row, Stripe state, or collected revenue. Sales
metrics computed from it (counts, call→signup rate) measure sales-stage
progress only. A safe, explicit linking mechanism from a sales prospect
to a real TallyVis business (for when a prospect actually signs up and
creates an account) would fit this architecture cleanly later — it was
not built now, to avoid expanding V1 beyond what tomorrow's calling
session needs.

## Intentionally deferred

Per the brief's own explicit list, confirmed not built: Twilio/browser
calling of any kind (TallyVis never dials — Kyle dials by hand), call
recording, transcription, AI call summaries, automated follow-up
emails/SMS, full CRM functionality (pipelines, deal stages beyond a call
outcome, tagging, bulk editing), sales forecasting, revenue attribution,
and multi-sales-rep functionality (the schema scopes "one active call"
per `started_by_user_id` and could support more than one rep without a
redesign, but no per-rep assignment/visibility UI exists — there is
exactly one real admin today). Also deferred: website/domain-based
duplicate matching (see "Duplicate detection" above), a "force import a
flagged row anyway" override, and any charting beyond the plain
`MetricCard` numbers already used elsewhere in this admin dashboard.
